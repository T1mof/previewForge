# Нагрузочные и отказные испытания

`stressbench` — тестовый Go runner в `test/e2e/stress`, запускаемый общим
`scripts/e2e.sh` после monitoring и сетевых проверок. Он использует только новый
локальный kind, созданный текущим запуском. Внешний кластер не нужен.

## Профиль

- 16 PreviewEnvironment, четыре параллельных автора запросов; четыре worker
  reconcile в операторе. Ещё четыре окружения нужны для проверки TTL.
- Заранее загруженный `previewforge-netprobe:<cluster>`, restricted Pod Security,
  requests 10m CPU / 16Mi, limits 100m CPU / 64Mi на приложение.
- Создание с одной репликой, увеличение до двух, исправление drift до трёх
  обратно к двум; после отказов — переходы к одной и двум репликам.
- REST-клиенты: каждый настроен на QPS 20, burst 40; это не общий лимит
  на все клиенты процесса. Пять пакетных List на наблюдение, интервал 1 с.
  UID/ownership дочерних ресурсов дополнительно проверяются после readiness.
- Общий deadline runner — 12 минут; отдельные ожидания ограничены. При ошибке
  восстановление control Deployment и очистка fixtures получают ещё до 3 минут.

Это ограниченный профиль для воспроизводимой демонстрации. Он не определяет
предельную ёмкость, production SLO, cold image pull или поведение большого кластера.
Количество namespace, маленькая нагрузка приложения, ресурсы runner и наблюдения
самого теста влияют на результат. Kubernetes version matrix — отдельная работа.

## Измерения

`artifacts/stress-report.json` содержит исходные задержки и nearest-rank
p50/p95/max: при N=16 p95 совпадает с максимумом. Для создания отсчёт начинается
перед Create, для spec update и drift — перед записью. Успех требует текущего
поколения CR, Ready condition, актуального Deployment и нужного количества
Running/Ready Pod с правильной цепочкой UID Pod → ReplicaSet → Deployment → CR.
В отчёте сохраняются UID Pod и поколений для каждой readiness-фазы.

Задержки включают API, ограничение параллелизма и polling. HTTP проверяется
отдельно через DNS и ClusterIP Service из настоящего Pod приложения. Проверка
владения после readiness и запуск HTTP добавляют время к общему эксперименту.
`wall_seconds` readiness-фазы начинается при входе в ожидание после записей;
это не длительность всей волны Create/Update.

Для восстановления отсчёт начинается перед возвратом сервера admission или
оператора; задержки включают его запуск, backoff и rollout. Очистка измеряется
до NotFound **и CR, и Namespace**. Удаление fixtures не снимает finalizers.
В `backlog-cleanup` опрос удаляемых CR/Namespace начинается после ожидания Ready
выживших окружений. Поэтому эта задержка включает последовательное ожидание
и является верхней границей первого наблюдения, а не точным моментом работы GC.

Каждые 5 с runner опрашивает Prometheus через API service proxy: RSS, CPU seconds,
rate CPU за минуту, очередь, ошибки reconcile, up. Сохраняются ответы с временными
метками и labels. Пропущенная серия не превращается в ноль. Максимальный
наблюдённый RSS/queue — максимум выборки, а не гарантированный пик; CPU rate —
среднее число ядер за окно, не CPU всего узла. Окно CPU может пересекать фазы.
Во время остановки оператора допустимы отсутствующие серии и stale samples.
Счётчики до и после перезапуска нельзя вычитать как один непрерывный процесс.

## Отказы

1. Admission Deployment масштабируется в 0. Dry-run записи настоящей identity
   оператора должен получить конкретную ошибку вызова ownership webhook.
   Изменения spec 16 окружений и удаления четырёх Deployment остаются ожидающими.
   После возврата admission все приложения восстанавливаются; UID и restart
   counters Pod оператора сохраняются, счётчик ошибок reconcile растёт.
2. Оператор масштабируется в 0 с ожиданием исчезновения Pod. В отсутствие
   контроллера меняются spec 12 окружений, удаляются четыре Deployment и четыре
   CR. Ещё четыре работающих окружения пересекают TTL, вычисленный от исходного
   creationTimestamp. Приложение продолжает отвечать HTTP во время простоя.
3. В status одного удаляемого CR подставляется имя foreign Namespace с canary.
   Этот Namespace также имеет поддельные managed labels. После возврата оператора
   сохраняются UID/resourceVersion Namespace и ConfigMap; собственные окружения
   удаляются по настоящему владельцу. Оставшиеся приложения достигают Ready.
4. Удаляются оставшиеся fixtures; все 20 CR и их Namespace должны исчезнуть.

Это управляемая остановка Deployment, не SIGKILL, падение узла, отказ API server,
сетевая partition или смена лидера при двух живых кандидатах. Ошибки API 429,
stale cache и конфликты не инъектируются этим runner; соответствующие unit/envtest
проверки не следует выдавать за результаты этого эксперимента.

## Запуск и границы доступа

Используйте обычный `make test-e2e` либо `scripts/check.ps1` и Git Bash
`PATH="$PWD/bin:$PATH" bash scripts/e2e.sh`. Требуются Docker, Calico, kind,
kubectl и Helm согласно [VERIFICATION.md](VERIFICATION.md). CI собирает runner
и запускает тот же полный suite. После добавления этого блока gate требует
22 check ID с Helm или 21 с явным Kustomize; новые ID — `load`, `faults`.

Wrapper проверяет claim/token и локальный Docker endpoint. Runner требует
точные run-dir/kubeconfig/context, claim текущего запуска, loopback HTTPS API
с проверкой TLS и явный source Namespace UID. Нельзя запускать его с произвольным
kubeconfig. Существующие имена fixtures не принимаются под управление.
Все Update используют свежий resourceVersion, Delete — исходный UID и свежий
resourceVersion. Замена UID разрешена только для явно удалённых Deployment.
Canary принадлежит тесту, но не оператору; тест удаляет его по UID своего Create.

После проверки доступа отчёт при ошибке сохраняется как `success: false`.
Отказ preflight не создаёт отчёт о Kubernetes-испытаниях. Незавершённый прогон, fake
client и synthetic report gate не подтверждают Kubernetes readiness или HTTP.
Публикуются только реально полученные измерения с commit, CI run, digest artifact
и подтверждённым cleanup; результат прежнего Helm suite не подтверждает новые
нагрузочные сценарии.

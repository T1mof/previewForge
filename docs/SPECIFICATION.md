# Техническое задание: PreviewForge

Ты — опытный Go Backend / Platform Engineer. Твоя задача — разработать полноценный open-source pet-проект на Go, который я смогу представить на техническом собеседовании на позицию Go Backend Intern в Яндексе.

Проект должен демонстрировать понимание Go, Kubernetes, системного программирования, отказоустойчивости, конкурентности, тестирования и автоматизации инфраструктуры.

**Мне нужен реально работающий, технически обоснованный проект, а не демонстрационный набор YAML-файлов.**

## 1. Концепция

Название: **PreviewForge**

PreviewForge — Kubernetes Operator для автоматического создания, управления и удаления изолированных тестовых окружений для Pull Request.

Проблема: разработчики тратят время на ручное развёртывание тестовых версий приложений, управление ресурсами и очистку ненужных окружений.

Решение: собственный Kubernetes Operator, написанный на Go, который управляет жизненным циклом таких окружений через Kubernetes API.

Пользователь описывает желаемое окружение через Custom Resource `PreviewEnvironment`, а контроллер самостоятельно создаёт необходимые ресурсы, отслеживает их состояние, восстанавливает при сбоях и удаляет по истечении TTL.

## 2. Технологический стек

Основные технологии:

- Go — основной язык.
- Kubernetes — платформа оркестрации.
- Kubebuilder и controller-runtime — разработка Operator.
- Docker — контейнеризация.
- kind — локальный Kubernetes-кластер.
- GitHub Actions — непрерывная интеграция и автоматизация.
- Prometheus — сбор метрик.
- Grafana — визуализация метрик.

Дополнительно при необходимости: Helm, Kubernetes RBAC, NetworkPolicy, Ingress.

Не добавляй PostgreSQL, Redis, Kafka и другие технологии без реальной необходимости. Проект должен концентрироваться на Kubernetes и системной Go-разработке.

Используй совместимые актуальные стабильные версии зависимостей. Не усложняй архитектуру без оснований.

## 3. Архитектура

Основные компоненты:

**PreviewEnvironment CRD**

Собственный ресурс Kubernetes, описывающий тестовое окружение.

Пример желаемого API:

    apiVersion: platform.previewforge.dev/v1alpha1
    kind: PreviewEnvironment
    metadata:
      name: pr-42
    spec:
      image: nginx:alpine
      replicas: 2
      port: 80
      ttlSeconds: 3600

Предпочтительно сделать ресурс уровня кластера (Cluster-scoped), чтобы корректно управлять жизненным циклом выделенного Namespace. Продумай владение ресурсами и правила Kubernetes garbage collection.

**Go Controller**

Контроллер, который:

- Отслеживает PreviewEnvironment.
- Сравнивает желаемое и фактическое состояние.
- Создаёт выделенный Namespace.
- Создаёт Deployment и Service.
- Отслеживает готовность приложения.
- Исправляет расхождения между желаемым и фактическим состоянием.
- Повторяет временно неуспешные операции.
- Обновляет Status и Conditions ресурса.
- Удаляет окружение по TTL.

Вся логика согласования состояния должна быть идемпотентной и безопасной при повторных вызовах.

**Жизненный цикл**

Предусмотри состояния Pending, Deploying, Ready, Failed, Expired.

Status должен содержать диагностическую информацию, позволяющую понять, почему окружение не готово.

**Изоляция**

Каждое окружение работает в отдельном Namespace. Нельзя допускать случайного изменения или удаления чужих ресурсов.

Используй ограничение CPU и памяти, корректные метки ресурсов и минимально необходимые разрешения RBAC.

## 4. Ключевые инженерные требования

### Отказоустойчивость

- После перезапуска контроллер восстанавливает управление окружениями.
- Повторная обработка событий не создаёт дублирующиеся ресурсы.
- При удалении подконтрольного Deployment контроллер восстанавливает его.
- Ошибки Kubernetes API обрабатываются корректно.
- При удалении PreviewEnvironment выполняется корректная очистка ресурсов.

### Конкурентность

- Корректная обработка нескольких PreviewEnvironment.
- Отсутствие конфликтов идентификаторов ресурсов.
- Безопасная повторная обработка событий.
- Безопасная работа при конфликтных обновлениях Kubernetes API.

### Тестирование

- Модульные тесты отдельных компонентов.
- Интеграционные тесты контроллера через envtest.
- Сквозные тесты в kind.
- Тестирование повторного согласования состояния, удаления ресурсов и ошибок API.
- Проверка поведения после перезапуска контроллера.

Не придумывай результаты тестирования — запускай проверки там, где доступна среда, и сообщай о реальных результатах.
